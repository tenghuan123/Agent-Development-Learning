# 第五课：V4 —— Planning 与复杂任务工作流路由 (Task Decomposition, FSM & Dynamic Re-planning)

> **核心认知**：纯 ReAct 范式（Thought → Action → Observation）的本质是“局部贪心与单步推演”。面对跨模块、多阶段的长流程复杂开发任务时，纯 ReAct 会不可避免地陷入**“短视贪心、目标漂移（Goal Drift）与进度盲区”**。
>
> 解决之道不是盲目增加 Prompt 长度，而是引入**“基于确定性有限状态机（FSM）的 Plan 任务管理器 + Attention Anchor 进度锚点注入 + 动态重规划（Dynamic Re-planning）+ 工作流智能路由（Workflow Routing）”**。

---

## 1. 核心矛盾：为什么纯 ReAct 面对复杂任务会变成“无头苍蝇”？

在第 3 课和第 4 课中，我们实现了 Agent Loop 和 Coding 自愈能力。当面对一个单点明确的 Bug 时（如“修改第 20 行类型报错并跑测试”），ReAct 表现得非常出色。

然而，当我们给 Agent 一个真实的综合性开发任务：

> **“帮我把项目里的内存存储重构为 SQLite，新增 `/api/todos` 的 CRUD 路由，编写单元测试验证，最后更新 README 的 API 文档。”**

在纯 ReAct 架构下，往往会出现以下灾难性现象：

```text
                               【纯 ReAct vs 结构化 Planning】

   纯 ReAct (走一步看一步 / 局部贪心):
   ┌────────────────────────────────────────────────────────────────────────┐
   │ 读代码 ──► 遇到某个小类型报错 ──► 陷进兔子洞修了 8 步 CSS/无关类型 ──►   │
   │ 💥 弊端: 严重目标漂移 (Goal Drift)、耗尽步数、漏做路由、忘写测试与文档    │
   └────────────────────────────────────────────────────────────────────────┘

   Planning Agent (全局规划 + 动态状态机追踪):
   ┌────────────────────────────────────────────────────────────────────────┐
   │ 1. 拆解大目标为明确步骤 (Todo List)                                      │
   │ 2. 实时状态机追踪: [✔] 探索分析 ──► [▶] 实现 SQLite ──► [ ] 路由 ──► [ ] 测试│
   │ ✨ 优势: 进度锚点锁定注意力、动态重规划 (Dynamic Re-plan)、绝不遗漏目标     │
   └────────────────────────────────────────────────────────────────────────┘
```

### 纯 ReAct 在复杂场景下的三大顽疾：
1. **短视贪心（Myopic Execution）**：模型每一步只看最新 1~2 步的 Observation，走一步看一步。一旦遇到支线插曲（例如某个无关警告），模型就会被带偏，彻底陷进“兔子洞”（Rabbit Hole）；
2. **目标漂移（Goal Drift）**：随着执行步数增多，上下文越来越长，最初的用户 Prompt 被挤到最顶端，注意力被稀释，模型会**“忘记后面还有哪些事没做”**；
3. **黑盒无感知与早停/过载（Progress Blindness）**：用户不知道 Agent 目前完成了整体的百分之几，Agent 自身也缺乏进度感知，经常在只做完一半时就自信汇报“已完成”，或者盲目乱跑直至耗尽 Max Steps。

## 2. 确定性有限状态机（Finite State Machine）设计

许多初学者的误区是让大模型在纯文本里写 `Step 1: ..., Step 2: ...`。这种做法极其脆弱，因为 LLM 经常会产生幻觉跳步、漏步。

在工业级系统（如 Claude Code）中，**任务状态不保存在模型的脆弱记忆里，而是由宿主 Runtime 维护一个外部强类型的确定性状态机（PlanManager）**：

```text
               ┌─────────────┐
               │   PENDING   │ (待执行)
               └──────┬──────┘
                      │
                      │ 触发 start_task (全局同一时刻至多 1 个)
                      ▼
               ┌─────────────┐  测试失败/遇到未知阻碍 ┌─────────────┐
               │ IN_PROGRESS │ ────────────────► │   BLOCKED   │ (阻塞待重规划)
               └──────┬──────┘ ◄──────────────── └─────────────┘
                      │          解除阻塞
                      │ 触发 complete_task (需附带验证凭据 summary)
                      ▼
               ┌─────────────┐
               │  COMPLETED  │ (已完成，状态不可逆)
               └─────────────┘

       [特殊流转 - 动态重规划 Re-planning]
       PENDING / BLOCKED ──► SKIPPED (已废弃/跳过)
```

### 状态机的三大约束准则（Invariants）：
1. **单一焦点准则（Single Focus Invariant）**：
   - 任何时刻，系统中**至多只能有 1 个任务处于 `IN_PROGRESS` 状态**。这能强迫 Agent 集中所有 Attention 攻克当前单点，杜绝“同时改 3 个文件导致上下文混乱”。
2. **强制完成凭证（Completion Evidence）**：
   - 当模型调用 `complete_task` 时，不能只传个状态，必须提供 `resultSummary`（如：“已在 `db/sqlite.ts` 中实现表初始化，并通过连接测试”）。
3. **已完成不可逆（Immutability of Done）**：
   - 处于 `COMPLETED` 的任务默认不允许随意回退，防止模型在遇到后期挫折时去篡改已完成成果，破坏整体进度。

## 3. 灵魂设计：Attention Anchor 进度锚点注入

在每一轮 Agent Loop 执行前，`PlanManager` 会自动将当前状态机渲染成一段高对比度的文本，**置顶注入到模型的上下文或系统提示中**：

```text
======================= 🎯 CURRENT EXECUTION PLAN =======================
Goal: 将内存存储重构为 SQLite，新增 /api/todos 路由并补齐测试
Progress: [██████████░░░░░░░░░░] 50% (2/4 Tasks Completed) | Revision: 1

[✔] task_1: 探查当前内存存储实现与路由依赖
    └─ Verified: 查明现有 store.ts 导出内存 Map，routes.ts 引用了 getTodos
[▶] task_2: 编写 sqlite.ts 封装 better-sqlite3 数据库连接与表初始化  <-- 【CURRENT FOCUS】
[ ] task_3: 重写路由处理函数对接 SQLite CRUD
[ ] task_4: 运行 npm test 验证全流程并修复潜在回归问题

⚠️ ATTENTION CONSTRAINT:
You are currently working on task_2. Stay focused on this task only.
Do NOT jump ahead to task_3 or task_4 until task_2 is verified and marked completed.
========================================================================
```

### 为什么 Attention Anchor 具有决定性作用？
1. **彻底杜绝早停幻觉**：模型看到 `Progress: 50%`，绝不会在只做了 2 步时就误以为全部完成；
2. **锁定注意力焦点**：显式提示 `[CURRENT FOCUS]`，模型的生成方向被牢牢约束在当前单点任务上；
3. **精简保留历史上下文**：前序任务的完成结论（`Verified` 摘要）被浓缩保留，模型无须在万行历史日志中反复回溯。

## 4. 动态重规划（Dynamic Re-planning）机制

软件工程中，**静态的计划往往在接触真实环境的第一秒就面临变更**。

例如：
1. Agent 初始计划：“使用 `better-sqlite3` 搭建本地数据库”；
2. 在第 1 步探查中，Agent 发现当前沙箱环境缺少 C++ 编译工具链，原生模块无法编译；
3. **此时如果没有动态重规划，Agent 将在死胡同里无限报错直至耗尽步数**。

通过 `manage_plan` 的 `replan` 动作：
- Agent 识别到约束阻碍；
- 调用 `replan({ reason: "环境缺少 node-gyp 原生编译链，切换为轻量 JSON 文件持久化", tasks: [...] })`；
- Plan 的版本号自增为 `Revision 2`，保留已完成的前置调研结论，平滑更新后续任务列表。

## 7. 工业级实战复盘：环境盲区、言语空转与工业界三大流派 (Engineering Insights)

在真实工程落地与测试中，我们捕捉到了几类极具代表性的 Agent 经典故障与认知死穴：

### 1. 经典痛点一：空中楼阁式的盲目规划（Environment Blindness）
- **现象**：Agent 一拿到任务，未经任何实际探查就急于拆解任务，凭空脑补了不存在的测试工具（如盲目假设项目装了 `jest`）或忽略了运行时的模块规范（如在 Node ESM 中省略了 `.ts` 扩展名）。
- **根因**：规划前置了，探索后置了。建立在虚妄假设之上的 Plan，从诞生的第一秒起就注定在执行阶段处处碰壁。

### 2. 经典痛点二：言语承诺代替实际行动（Action Verbalization & Context Echo）
- **现象**：当命令报错时，模型在 Thought 中说 *“由于遇到了错误，我将重新检查并修复代码...”*，但**该轮次没有输出任何 Tool Calls**。在随后的步骤中，由于自回归 Attention 聚焦在上一轮自己说的话上（Context Echo），导致模型一字不差地复读这段废话，直至耗尽步数预算退出。
- **根因**：模型在遭遇挫折时倾向于输出“口头表态”这种计算阻力最小的 Token 序列，而 Runtime 缺乏硬性动作强制拦截。

### 4. 遇到错误时：局部自愈（Local Patching）vs 全局重规划（Re-planning）

工业界的共识分级原则：
1. **小错绝不 Re-plan（Local Fix）**：
   - 缺少扩展名、类型拼写错误、单点用例未通过等，由单步 ReAct 自愈（`read_file` ➔ `edit_file` ➔ `run_command`）在原地 1~2 步内修好，严禁触发重置状态机的大动作；
2. **大错才 Re-plan（Escalation Trigger）**：
   - 依赖缺失且无法安装、底层架构假设被推翻时，由 Supervisor 监督层或 Agent 主动触发 `replan` 动作，记录 `replanReason` 并平滑迁移任务列表。

### 5. Mini Claude Code 的防护架构落地

在本课的工程代码中，我们落地了以下防御机制：
1. **Zero-turn Auto-Grounding（第 0 步环境自动预感知）**：
   - 在启动规划前，宿主 Runtime 自动扫描 `package.json`（模块类型、依赖、脚本）及 Node.js 版本，生成 `PROJECT RUNTIME CONTEXT` 注入 System Prompt，消除环境盲区；
2. **Anti-Verbalization Action Forcing Guard（防言语空转强制动作守卫）**：
   - 当任务处于 `[IN PROGRESS]` 时，若模型仅输出纯文本意图而无任何 Tool Call，Runtime 立即进行硬拦截并强迫其调用具体工具（`edit_file` / `run_command` / `manage_plan`），坚决掐死“只说不做”的复读绕圈；
3. **Fallback Tool Call Extractor（文本工具提取容错器）**：
   - 兼容部分开源大模型在长上下文中以 Markdown / JSON 纯文本形式输出工具调用的情况，自动提取并恢复为标准 Tool Calls 执行。
