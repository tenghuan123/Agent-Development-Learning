# 第 3 课：数据很多怎么找到相关信息？—— 词法检索与关键词提取 (Lexical Search & Grep)

> **核心目标**：彻底告别“全量灌入模型”的蛮力时代。从计算机工业界最稳健、零算力浪费的底层原语出发，手写关键词提取、纯文本词法匹配（Grep/Substring）与按需文档读取闭环，建立检索增强生成（RAG）的最原始形态，并亲历词汇鸿沟（Vocabulary Mismatch）引发的检索塌方。

---

## 1. 承前启后：为什么检索是必然选择？

在上一课（第 2 课）中，我们打破了“长上下文时代可以无脑全塞”的幻想：
- **Token 爆炸**：数十篇文档全塞让单次成本飙升 80+ 倍；
- **首字延迟卡顿**：Prefill 预填充阶段构建全量注意力 KV-Cache，TTFT 延迟从 300ms 恶化到数秒；
- **注意力迷失**：夹在长文本正中间的关键信息（Lost in the Middle）极易被模型忽略，导致答错或幻觉。

我们得出了第一条守恒铁律：
> **不是 Maximum Context，而是 Sufficient Context（充分必要上下文）。**

但这个结论立刻把我们推到了悬崖边：
```text
真实知识库：
10,000 篇产品手册、技术规范、客服问答、历史政策
               ↓
模型无法一次性全部阅读（不仅爆窗，且成本与延迟均不可接受）
               ↓
用户随时发起一次提问：“Alpha 产品的退款期限是多少天？”
               ↓
工程核心矛盾：
在完全不让模型预读 10,000 篇文档的前提下，系统怎么精准挑出【仅包含充分事实】的那 1 篇文档？
```

**答案只有一个：检索（Search）。**

## 2. 为什么严禁在第一天引入 Vector DB / Embedding？

许多刚接触 LLM Agent 或 RAG 的开发者，最容易犯的一个重大架构错误就是：
> **“要做搜索，马上调包 OpenAI text-embedding-3-small，开一个 Chroma / Pinecone / Milvus 向量库，把文档切片做向量相似度检索。”**

在教学和工程第一性原理中，这是严重的**过度工程化（Over-Engineering）**与**认知跳步**：

| 维度 | 朴素质朴的词法检索 (Lexical Search / Grep) | 向量语义检索 (Vector Semantic Search) |
| :--- | :--- | :--- |
| **外部算力依赖** | **零依赖**。纯本地 CPU 字符串比对或倒排索引 | 强依赖 Embedding 模型推理（需消耗 GPU 算力或 API 账单） |
| **冷启动与建立时间** | **即时毫秒级**。无需批量离线向量化计算 | 巨型文档库需要数小时甚至数天执行预先向量化 |
| **精确标识符匹配** | **100% 绝对精确**。如错误码 `ERR_9021`、函数名 `AuthBridge` | **经常严重失真**。长串特定 ID 在向量空间中往往缺乏语义区分度 |
| **结果可解释性** | **完全透明白盒**。命中第几行、匹配哪个词一清二楚 | **黑盒高维浮点数**。无法直观解释为什么两段文字余弦为 0.78 |
| **维护与架构复杂度** | 极低。只需几行 TypeScript / Shell 代码即可工作 | 极高。索引构建、维数对齐、距离度量、内存膨胀 |

因此，**先用最朴素的词法匹配解决 80% 的精确事实问题**，只有当你亲眼看到它在哪种场景下彻底失败时，你才会真正明白后续技术（向量、混合检索、Reranker）的不可替代性。

## 3. 词法检索的三大核心原语

一个最小而完备的词法检索闭环由三个正交原语构成：

```mermaid
graph LR
    Q[用户原始提问] --> K[原语 1: extractKeywords 关键词提取]
    K --> S[原语 2: searchText 纯文本全库扫描]
    S --> R[原语 3: readDocument 按需加载目标文档]
    R --> C[装配 Sufficient Context]
    C --> M[LLM 最终生成严谨答案]
```

### 原语 1：关键词提取（`extractKeywords`）
用户提问往往包含大量口语化修饰词（如“请问一下”、“怎么处理”、“多少天”）。词法检索必须先滤除无意义的停用词（Stop Words），提取出高密度的关键信息：

```ts

  const codes = question.match(codeRegex) || [];
```

只有当检索确认命中了相关候选后，系统才调用 `readDocument(id)` 将该文档内容从磁盘读入内存，完成上下文装配：

## 4. 收益量化：词法检索的工程奇迹

当我们在基准语料库中，针对用户问题：“*Alpha 产品的退款期限是多少天？*” 运行这条检索流水线时，系统呈现出惊人的效率提升：

| 指标 | 第 2 课：全塞入模式 (Maximum Context) | 本课：词法检索模式 (Lexical Search Pipeline) | 效益对比 |
| :--- | :--- | :--- | :--- |
| **读取文档数** | 8 篇全部读入 | 仅读取 1 篇最佳命中 (`products/alpha.md`) | **文档读取量减少 87.5%** |
| **输入 Prompt Tokens** | ~10,400 Tokens | ~450 Tokens | **Token 消耗锐减 95.7%** |
| **检索耗时 (Latency)** | 0ms (不搜索) | **< 3ms** (纯 CPU 字符串快速扫描) | 毫秒级极速定位 |
| **LLM 生成耗时 (TTFT)** | 3,800ms ~ 5,200ms (庞大 Prefill) | **320ms** (极小 Prefill) | **首字响应速度提升 12 倍** |
| **单次推理预估成本** | \$0.0104 | \$0.00045 | **单次调用成本节省 95.7%** |
| **信噪比 (SNR)** | < 4% (充斥无关条款) | **> 90%** (纯粹充分必要事实) | 彻底消除注意力衰减与事实混淆 |

**结论**：哪怕仅仅加了一个最简单的 `searchText()`，整个 Agent 系统的成本、延迟和抗幻觉能力就跨越了一个时代！

## 5. 核心实验与物理死穴（The Lexical Trap）

既然词法检索如此轻量、毫秒级、且零算力浪费，**我们是不是可以永远不用学向量和语义检索了？**

本课通过两组极具代表性的真实测试用例，带你撞上词法检索不可逾越的物理高墙：

### 实验 A：精确标识符与技术符号（词法检索的高光时刻 🌟）
- **提问**：“遇到错误码 `ERR_ALPHA_AUTH_9021` 应该如何处理？”
- **关键词提取**：`["ERR_ALPHA_AUTH_9021"]`
- **检索结果**：
  - `products/alpha.md`：**100% 精确命中**（出现频次 1，得分极高，提取出专属 SSO 令牌处理措施）；
  - 其他无关文档：0 命中；
- **模型回答**：“该错误表示企业 SSO 令牌过期，需要管理员在控制台重新颁发授权密钥并重启 AlphaSyncDaemon。”（严谨、毫秒级返回、100% 确定性）。

### 实验 B：口语同义词与自然表达（词法检索的灾难崩塌 💥）
- **提问**：“我买完东西以后**后悔了**、**不想要了**，还能申请退款吗？”
- **关键词提取**：`["后悔", "不想要"]`
- **检索结果**：
  - `docs/refund-policy.md` 实际内容：`所有标准数字软件与 SaaS 订阅商品均全面支持 7 天无理由退款。用户在订单完成后的 7 天犹豫期与冷静期内，均可无障碍申请全额原路退款。`
  - 检索执行：全库文档没有任何一个字包含“后悔”或“不想要”！
  - **命中结果：0 条记录！**
- **模型回答**：
  - 系统因未检索到任何匹配文档，只能向模型传递空上下文；
  - 模型无法获取“7 天无理由退款”的官方政策，只能回答“抱歉，私有知识库中缺乏相关退款规定”。

## 6. 词法检索的物理边界剖析

通过实验 B，我们清晰提炼出了词法检索无法逾越的**三大词汇鸿沟（Vocabulary Mismatch）**：

1. **同义异形（Synonymy）**：
   - 用户说：“*后悔了 / 不想要了*”
   - 文档写：“*7 天无理由退换 / 犹豫期*”
   - 字符不同，但表达的业务含义完全相同。纯字符串匹配无法感知二者的语义等价。
2. **多义异实（Polysemy）**：
   - 用户搜：“*苹果退款*”
   - 系统可能把“*水果生鲜售后政策*”和“*Apple iOS 应用内购买规则*”同时检索出来，字面上都含“苹果”，但语境天差地别。
3. **拼写误差与语法变形（Morphology）**：
   - 用户写了错别字或英文复数、动词变位（如 `pricing` vs `price`），简单词法匹配很容易失真或遗漏。

## 7. 核心验收标准与认知确立

完成本课学习后，你必须牢固确立以下两条工程原则：

### 铁律一：检索是实现 Sufficient Context 的第一生产力
> **绝不能依靠加大上下文窗口来解决知识库容量问题。必须通过前置检索将万级语料精准过滤为单篇或少数几篇高信息密度文档，再装配送入模型。**

### 铁律二：词法检索是工程底线，但不是终点
> **词法检索擅长找“字”（精确代码、特定产品名、固定术语），但绝不擅长找“意思”（自然语言表达、口语提问、泛化意图）。**
