## 2. 核心第一性原理：单元自足率与信噪比的 U 形博弈

### 2.1 两个指标的物理对抗

在评测切片检索系统时，必须建立两个核心指标的度量：
1. **切片信噪比（Signal-to-Noise Ratio, SNR）**：
   $$\text{SNR}(C) = \frac{|\mathcal{F}_{\text{gold}} \cap C|}{L(C)}$$
   衡量注入内容的有效信息浓度。切片越小，SNR 理论上越高。
2. **单元自足率（Unit Completeness Rate）**：
   $$P_{\text{self-sufficient}} = P(\mathcal{F}_{\text{gold}} \subseteq C_{\text{top1}})$$
   衡量检索命中的 Top-1 最小单元，自身是否**完整闭合地包含了推导答案所需的全部前因后果**。

```text
  指标表现
    ▲
100%│ 完整性与单元自足率 P(self-sufficient)
    │                  /─────────────────────────── (整篇文档: 100% 自足)
    │                 /
    │                /  【两难深渊】
    │               /   小切片: 虽能命中关键词，但半句话讲不明白
    │              /    大切片: 语境完整，但信噪比暴跌至 < 0.5%
    │  信噪比 SNR /
    │    \       /
    │     \     /
    │      \   /
    │       \ /
    │        X
    │       / \
    │      /   \
    │     /     \
    │    /       \──────────────────────────────── (整篇文档: SNR 0.46%)
  0%└──────────────────────────────────────────────► 切片粒度 (Token 预算)
      64      256        512         1024     2048+
    (切碎)  (语义失真) (黄金平衡点) (开始稀释) (巨型长文)
```

### 2.2 实测基准给出的残酷数据

在 `docs/ops-handbook.md`（5,688 Token，16 章节，6 条黄金陷阱测试用例）上展开的控制变量扫描证实了这一矛盾：

| 切分策略与粒度 | 平均单次注入 Token | 平均信噪比（SNR） | **单元自足率** | **高信噪比完整率** | 核心失效表征 |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **整篇文档（退化基线）** | 7,825 | $0.46\%$ | **$100\%$** | **$0.0\%$** | 答案被 99.5% 的无关文本淹没，信噪比不及格 |
| `fixed-2048`（过大） | 5,239 | $0.73\%$ | $50.0\%$ | **$0.0\%$** | 切大无用，信噪比仍低于 1%，稀释依旧 |

| `fixed-256`（过碎） | **755** | **$4.83\%$** | **$16.7\%$** | $50.0\%$ | **单元自足率暴跌至 16.7%**！仅 1/6 的切片能自圆其说 |

> **核心结论**：
> 如果检索单元直接等于注入单元，你永远只能在“断章取义”和“注意力稀释”之间二选一！

## 3. 切片检索的三大恶性陷阱与实测反例

基于我们搭建的基准测试集，以下三大陷阱是切片检索在生产环境中最常见的“滑铁卢”：

### 陷阱 1：孤岛代词与主语失窃（Orphan Anaphora Trap，基准用例 `ck-05`）

- **原文语境**：
  ```markdown
  ## 8. 容灾与双活机制
  当主备切换在 90 秒内未能完成时，视为跨可用区切换失败。
  
  [切片下刀边界]
  
  这种情况下，须在 15 分钟内触发全局熔断并进入只读模式。
  ```
- **用户提问**：*“什么情况下需要触发全局熔断？”*
- **踩坑现象**：
  - 后一个切片包含“*这种情况下，须在 15 分钟内触发全局熔断……*”，但压根没有“*跨可用区切换失败*”这八个字！
  - 检索器如果根据“全局熔断”命中了后切片，由于切片内缺乏先行词（Antecedent），模型面对的是一个逻辑孤岛；
  - 检索器若检索“切换失败”，又完全找不到后半句的“全局熔断”。

### 陷阱 2：等权融合稀释陷阱（Equally Weighted Fusion Dilution，基准用例 `ck-04`）

- **用户提问**：*“演练复盘要求多久组织一次？由谁主持？”*
- **踩坑实测**：
  - **词法通道（Lexical）**：切片粒度变小后，关键词密度极高，目标切片以 **Score = 33 分**压倒性拿下第 1 名（第 2 名仅 12 分）；
  - **融合阶段（RRF）**：等权倒数排名融合计算公式为 $\text{RRF} = \frac{1}{60 + \text{rank}_{\text{lex}}} + \frac{1}{60 + \text{rank}_{\text{sem}}}$。由于该切片的语义弱向量给出了低名次（Rank 15），RRF 等权折算后，目标切片直接被**挤出候选池 Top 12**！
  - **教训**：在小切片体系下，词法信号的极端尖峰极易被等权 RRF 算法平滑稀释。

### 陷阱 3：脆弱性反噬与张冠李戴幻觉（Fragility Escalation Trap）

对比端到端三种注入方式：
```text
用户提问：“演练复盘要求多久组织一次？由谁主持？” (ck-04)

【路径 A: 文档级注入（5,688 Token）】
  模型回复：“演练复盘要求每两周组织一次，由平台工程部主持。”  ──► 正确！
  机理：虽然信噪比只有 0.46%，文档很长，但证据 100% 在里面，模型硬找找到了。

【路径 B: 纯切片精排注入（748 Token，检索脱靶）】
  模型回复：“资料中并未明确指出复盘的具体频率和由谁主持……”    ──► 答不出！

【路径 C: Small-to-Big 展开注入（748 Token，展开了错误邻域）】
  模型回复：“容灾切换演练每半年至少一次……演练复盘要求每半年组织一次。” ──► 严重幻觉！
  机理：切片检索把第 9 章的“容灾切换演练”当成了目标，模型为了强行答题，
       把“半年”张冠李戴嫁接到了“演练复盘”上！
```

> **高危警示：切片工程的终极法则**
> 切片化把检索质量从**“影响答案好坏”**升级成了**“影响答案有无与真伪”**。
> 整篇文档注入的最坏情况是“模型答得啰嗦”，而切片脱靶的最坏情况是“模型言之凿凿地编造伪证”。

## 4. 语料变换层与 Small-to-Big 两级架构

面对单元自足率与信噪比的深渊，工业界的标准破局思路是：**将检索栈与注入栈彻底解耦**。

### 4.1 语料变换层（Corpus Transformation Layer）设计

在系统分层上，切片不是一种新的检索算法，而是位于检索栈底部的语料变换层：

```text
CorpusDocument[] (原始大文档)
       │
       ▼  chunkDocument()                   ← C8 切分引擎
Chunk[] (切片数据结构)
       │
       ▼  toChunkDocument()                 ← 零侵入投影层：title = "文档名 > 章节路径"
CorpusDocument[] (投影切片文档)
       │
       ├──► searchInDocs()                  ← C3 词法检索（零改动复用）
       ├──► searchSemanticInDocs()          ← C4 向量检索（零改动复用）
       ├──► reciprocalRankFusion()          ← C6 混合融合（零改动复用）
       └──► rerankDocuments()               ← C7 Cross-Encoder 精排（零改动复用）
       │
       ▼  Top-K 命中切片
expandToParent()                            ← Small-to-Big 向上展开父窗口
       │
       ▼
Golden Context 注入 Prompt
```

通过投影函数 `toChunkDocument`，切片携带自身的祖先标题面包屑（如 `ops-handbook > 故障响应 > P2处理`）伪装成独立的 `CorpusDocument`，上层 C3~C7 的所有 BM25、语义向量、RRF 融合与 Cross-Encoder 算子**无需修改一行代码**即可直接运行！

### 4.2 Small-to-Big（父子块展开）算法实现

**核心思想**：
- **Child Chunk（小切片，256 Token）**：专门用于向量化与倒排索引。小切片主题极度聚焦，均值池化（Mean Pooling）零失真，Cross-Encoder 计算开销极低；
- **Parent Chunk（大窗口，1,400 Token）**：当 Child Chunk 被高分命中后，系统以命中切片为锚点，向上下文中双向贪心吞吐相邻切片，还原完整上下文后再注入 Prompt。

```typescript
export function expandToParent(
  allChunks: Chunk[],
  hit: Chunk,
  options: { parentSize: number }
): Chunk[] {
  const budget = Math.max(hit.tokenCount, options.parentSize);
  const sameDoc = allChunks
    .filter((c) => c.docId === hit.docId)
    .sort((a, b) => a.index - b.index);
  const pos = sameDoc.findIndex((c) => c.id === hit.id);
  if (pos === -1) return [hit];

  // 边界铁律：严禁跨越顶级章节（Section Boundary）
  const hitSection = hit.sectionPath.join(" > ");
  let left = pos;
  let right = pos;
  let usedTokens = hit.tokenCount;

  // 交替向两侧吞吐扩展，保持命中的 Child Chunk 居中
  while (true) {
    const prevOk =
      left - 1 >= 0 &&
      sameDoc[left - 1].sectionPath.join(" > ") === hitSection &&
      usedTokens + sameDoc[left - 1].tokenCount <= budget;

    const nextOk =
      right + 1 < sameDoc.length &&
      sameDoc[right + 1].sectionPath.join(" > ") === hitSection &&
      usedTokens + sameDoc[right + 1].tokenCount <= budget;

    if (!prevOk && !nextOk) break;

    if (prevOk) {
      left--;
      usedTokens += sameDoc[left].tokenCount;
    }
    if (nextOk) {
      right++;
      usedTokens += sameDoc[right].tokenCount;
    }
  }

  return sameDoc.slice(left, right + 1);
}
```

## 6. 工业界落地：存储解耦与安全防护

### 6.1 存储拓扑解耦：VectorStore 与 DocStore

在工业级生产架构中，绝不能将切片的全部文本直接堆在向量数据库的元数据里。标准实践是**存储解耦**：

```text
                       [ 用户查询 Query ]
                               │
                ┌──────────────┴──────────────┐
                ▼                             ▼
       [ 向量数据库 VectorStore ]       [ 倒排索引 Lexical Index ]
       - 存储 Child Chunks 向量       - 存储 Child Chunks 文本词频
       - 极高维度，小 Payload         - 快速符号倒排
                │                             │
                └──────────────┬──────────────┘
                               ▼
                       Top-K 命中 Child ID
                               │
                               ▼
                  [ 文档数据库 DocStore / KV ]
                  - Key: Child ID
                  - Value: 向上展开的 Parent Chunk (1400 Token)
                  - 存储成本极低，极速读取大段文本
                               │
                               ▼
                        注入 LLM 上下文
```

### 6.2 向量集生命周期与维度安全防护

在切分系统迭代过程中，必须严格执行三项工程防御铁律：
1. **切分配置与向量集强哈希绑定**：切分参数变化后切片 ID 对应的文本彻底改变，向量集文件名必须编码切分参数（如 `chunk-recursive-512-ov64.json`）；
2. **异维余弦静默降级熔断**：当查询向量与切片向量发生维度错配时，坚决不能强行计算截断点积，必须直接触发熔断并干净回退至纯本地向量通道；
3. **整篇兜底与强否定约束**：当切片检索的最高分低于动态置信度阈值时，系统应触发回退机制，直接调取源文档整篇注入；同时 System Prompt 必须包含：“当提供的内容不足以推导出答案时，必须明确回答未知，严禁臆造伪证”。

## 7. 思考题与第 10 课预告

### 7.1 第一性原理思考题

1. **两级维度的物理本质**：Small-to-Big 的“切片单元自足率”只有 $83.3\%$，但“最终注入完整率”却达到了 $100\%$。请用一句话解释这两个指标分别在衡量系统哪个阶段的能力。
2. **存储分离的成本账本**：在千万级切片规模下，将 Parent Chunk 存储在 Key-Value Store（如 RocksDB / Redis / S3）而非 VectorStore Payload 中，能为向量检索集群带来多大幅度的内存（RAM）与 GC 开销节省？
3. **等权 RRF 的失效根因**：为什么在粗粒度切片下表现良好的等权 RRF（$k=60$），在细粒度切片下更容易把词法高分目标挤出候选池？

### 7.2 已知未解与第 10 课预告：Chunk 自己脱离语境没有意义怎么办？

通过本课，我们用 Small-to-Big 解耦了检索与注入的原子单位。
但是，基准用例 `ck-05` 像一根刺一样留在了评测报表里：

```text
某切片开头写着：“这种情况下，须在 15 分钟内触发全局熔断并进入只读模式。”
用户提问：“什么情况下需要触发全局熔断？”
```

面对这个切片，即使将其父窗口扩大一倍，由于主语“跨可用区切换失败”远在上一节的综述里，切片本身依然是一个**主语失窃的孤岛**！

> **切片在解决了信息过载的同时，不可避免地剥离了全局语境。**  
> **如果一个 Chunk 脱离了文档就失去了语义，检索器该怎么搜到它？**
