# 第 12 课：Agent 为什么会过度检索？—— 上下文控制、停机准则与预算调度（Context Control & Budget Management）

> **核心目标**：攻克智能体在获取自主检索能力后带来的最危险生产事故 —— **“过度检索死循环与 Token 账本失控（The Over-searching Trap & Budget Burnout）”**。深入剖析当提问包含未收录虚构实体、语义模糊近义词自旋或弱相关海量噪音时，智能体如何陷入无休止的“猜词盲搜”；从第一性原理严密推导 **边际信息增益递减定律（Law of Diminishing Marginal Returns）** 与 **多维预算硬墙（Multi-dimensional Budget Wall）**；手写 **Jaccard 词袋环路探测器**、**连续空命中熔断器** 与 **自适应增益早停机制**；在 6 大典型基准用例（含 4 大对抗陷阱）上对比四大控制策略，见证无效 Token 消耗暴降 **70%~90%** 且合法多跳任务 100% 保真完成，推开现代 Agent 上下文工程的治理控制之门。

## 1. 承前启后：C11 自主智能体留下的致命“刺”

在第 11 课中，我们推翻了“开发者替模型提前预先检索一次”的静态传统 RAG 假定，将检索工具原子化，让 Agent 通过 ReAct 循环实现了自主多跳推理，在复杂问题上的事实召回率从 $33.3\%$ 跃升至 **$100\%$**。

然而，在第 11 课评测矩阵的最后一行，测试用例 **`mh-05-trap`** 却刺眼地挂着一行异常监控：

```text
用例 mh-05-trap：
  用户提问：“产品 Delta 的量子加密协议支持哪些版本？与 Omega 缓存集群连接时默认同步时延是多少？”
  真实知识库状态：
    产品库仅收录 Alpha, Beta, Gamma 三款产品；
    知识库中根本不存在 Delta 与 Omega 任何记录！
```

### 1.1 无约束智能体的混沌暴走

在一个未设置精细预算控制的传统 Agent 运行时中，发生了如下失控行为：

```text
Step 1: search_text("Delta 量子加密 协议") ──► 0 结果
  ▼ (模型心想：字面没搜到，可能换个说法？)
Step 2: search_semantic("Delta 安全加密协议") ──► 命中 Alpha TLS 加密片段 (弱相关噪音)
  ▼ (模型心想：再搜搜 Omega 看看？)
Step 3: search_text("Omega 缓存集群 零拷贝") ──► 0 结果
  ▼ (模型心想：拆开搜 '零拷贝 时延'？)
Step 4: search_text("零拷贝 同步时延") ──► 命中 Alpha 内部总线 5ms
  ▼ (模型心想：还是没看到 Delta，我把所有文档目录看一遍！)
Step 5: read_doc_headings("products/alpha.md") ──► 无 Delta
  ▼
Step 6: read_doc_headings("products/beta.md") ──► 无 Delta
  ▼
Step 7: read_doc_headings("products/gamma.md") ──► 无 Delta
  ▼ (模型心想：最后再做一次全网泛化检索！)
Step 8: search_text("量子加密") ──► 0 结果
  ▼
Step 9: [触碰最大步数强制终止] 累计注入 2,140 Tokens，耗时 2.4 秒！
```

最终，模型不仅消耗了正常任务 3~5 倍的 Token 与 API 费用，而且因为第 2 步和第 4 步抓取了与 Alpha 相关的无关干扰切片，竟然在最终输出中发生严重的**指鹿为马（Distractor Hallucination）**：
> “根据系统文档，Delta 支持基于 TLS 的安全协议，与缓存集群同步默认时延低于 5ms。” —— **这是纯粹的幻觉捏造！**

> **核心困境**：  
> **给 Agent 搜索工具，解决了“信息获取”的能力；**  
> **但如果不教 Agent“什么时候停止”，自由就会沦为系统的灾难与负债！**

## 2. 核心第一性原理：过度检索的物理学与经济学

为什么 LLM 在遇到未知问题时会疯狂发散？这背后有深刻的模型动力学与信息论原因。

### 2.1 边际信息增益递减定律（Law of Diminishing Marginal Returns）

设目标问题为 $Q$，在检索探索的第 $k$ 步，Agent 已经收集到了状态上下文集合 $S_k = \{O_1, O_2, \dots, O_{k-1}\}$。
第 $k$ 轮工具调用返回的新观察为 $O_k$。我们定义第 $k$ 步的**边际信息增益（Marginal Information Gain）** $\Delta I(k)$ 为：

$$\Delta I(k) = H(Q \mid S_k) - H(Q \mid S_k \cup \{O_k\})$$

其中 $H(Q \mid S)$ 为在已知证据 $S$ 下关于目标问题的条件信息熵（即答案的不确定性）。

```text
边际增益 ΔI
  ▲
1.0 ┼───────┐
    │       │ (Step 1: 发现核心实体 85% 增益)
    │       │
0.5 ┼       └───────┐
    │               │ (Step 2: 补充关键边界 50% 增益)
    │               │
0.1 ┼               └───────────────────────────► 边际收益枯竭区 (饱和/噪音)
    │                                             (Step 3~8: 重复或无关)
0.0 ┴─────────────────────────────────────────────►
    0       1       2       3       4       5   Step
```

**物理规律**：
1. **有效信息高度集中在前 1~3 步**：对于任意有限知识库，解决一个事实性任务的关键证据通常高度紧凑。前 2 步即可消除 85% 以上的不确定性；
2. **后半程边际增益趋近于 0**：第 3 步之后如果仍无突破，继续执行盲目检索所获得的文本片段，其增益 $\Delta I(k) < \epsilon$；
3. **成本呈二次方加速上涨（$O(N^2)$ Prompt Inflation）**：Agent 每执行一轮工具调用，对话历史就会叠加数百 Token 的工具结果。这意味着每多执行一步，不仅消耗该步的 API 调用费，更让后续所有步骤的输入 Prompt 全面膨胀！

### 2.2 语义回音室与近义词自旋（Semantic Echo Chamber）

为什么模型自己不会停下来？
因为在自回归语言模型的目标函数中，**拒答（Saying "I don't know"）** 的概率被预训练和 RLHF 的“有用性（Helpfulness）”对齐严重压制。
模型倾向于假设：“一定是我用的检索词不够准确，换个同义词肯定能搜到！”

于是 Agent 展开了无意义的**同义改写死循环**：
- 搜“资费规则”无结果 $\to$ 改搜“计费模式”；
- 搜“计费模式”无结果 $\to$ 改搜“收费周期”；
- 搜“收费周期”无结果 $\to$ 改搜“扣费机制”。

这在信息论上称为**语义自旋（Semantic Spin）**：Query 的向量方向几乎完全重合，词袋重合度高达 80% 以上，却在空间中反复空转。

### 2.3 弱相关噪音反噬（Distractor-induced Hallucination）

最危险的过度检索不是 0 命中，而是**弱相关非空命中**。
当 Agent 搜“Omega 缓存时延”搜不到时，如果检索器返回了“Alpha 消息总线时延”，处于深层推理阶段的 LLM 在海量上下文注意力机制下，会出现注意力漂移，将无关数字拼凑进最终答案，导致幻觉率飙升。

## 3. 三大控制原语设计：从自由放任到自适应受控

为了彻底根治过度检索，我们必须在 Agent Runtime 层建立一套高内聚、沙箱化的**上下文控制有限状态机（Context Control FSM）**。

```text
                       ┌────────────────────────┐
                       │   Preflight Budget     │
                       │   飞行前静态硬墙检查   │
                       └───────────┬────────────┘
                                   │ 通过 (Safe)
                                   ▼
                       ┌────────────────────────┐
                       │    Tool Execution      │
                       │    执行原子检索原语    │
                       └───────────┬────────────┘
                                   │ 返回 Observation
                                   ▼
                       ┌────────────────────────┐
                       │ Post-step Evaluations  │
                       │ 边际增益与多维熔断判定 │
                       └───────────┬────────────┘
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         │                         │                         │
         ▼ (严重超标)              ▼ (饱和充分)              ▼ (正常受控)
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│ Circuit Breaked │       │   Early Stop    │       │    Proceed      │
│ 连续空召回/环路 │       │ 置信度达标早停  │       │ 继续探索下一步  │
└─────────────────┘       └─────────────────┘       └─────────────────┘
```

### 3.1 原语一：多维硬性预算墙（Multi-dimensional Hard Budget Wall）

系统绝不能依赖“模型的主动自觉”，必须由外层控制器设置不可逾越的物理硬墙：

```ts
export interface ContextBudgetConfig {
  maxTokens: number;                  // 总 Token 上限 (如 1600)
  maxToolCalls: number;               // 最大调用轮数 (如 6)
  maxConsecutiveZeroHits: number;     // 连续空召回熔断门限 (如 2)
  loopSimilarityThreshold: number;    // 环路探测 Jaccard 门限 (如 0.75)
  minMarginalGainThreshold: number;   // 边际增益早停门限 (如 0.10)
}
```

### 3.2 原语二：Jaccard 词袋环路探测器（Query Loop Detector）

如何在不调用昂贵 LLM 的情况下，用零延迟算法探测 Agent 是否在“近义词空转”？

我们设计了基于中英文 N-gram 与词袋（Bag of Words）的 **Jaccard 相似度探测器**：

$$J(Q_{\text{new}}, Q_{\text{prev}}) = \frac{|B(Q_{\text{new}}) \cap B(Q_{\text{prev}})|}{|B(Q_{\text{new}}) \cup B(Q_{\text{prev}})|}$$

当新 Query 与历史任意一次 Query 的相似度 $J \ge 0.75$ 时，控制器立即判定发生了同义词自旋，在执行工具前直接**就地熔断**，避免无谓的网络与磁盘 I/O。

### 3.3 原语三：边际信息增益量化器与早停准则（Marginal Gain $\Delta I$）

工具返回文本后，系统将新观察词袋 $B(O_k)$ 与已收集事实累积词袋 $B(S_{k-1})$ 进行差集分析：

$$\text{Gain}(O_k) = \frac{|\text{NovelTokens}(O_k \setminus S_{k-1}) \cap \text{Keywords}(Q)|}{|B(O_k)|}$$

- 若 $\text{Gain} < 0.10$ 且连续两步无实质新实体被发现，判定为**信息饱和（Information Saturation）**，触发主动早停；
- 若 Agent 上报的内部证据链置信度达到 $0.88$ 以上，同样触发充分度早停，绝不多搜一步。

## 4. 四大控制策略全景对决

在第 12 课实验工作台中，我们建立了一套覆盖正常合法多跳与对抗陷阱的基准用例库，横向对比 4 种控制机制：

| 策略代号 | 策略名称 | 核心机制 | 面对合法多跳 (`mh-01`) | 面对虚构陷阱 (`trap-01`) | 面对环路陷阱 (`trap-02`) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Strategy 1** | **自由放任 (Unconstrained)** | 无任何预算限制，任由 Agent 决定何时停止 | 召回率 100%，消耗 1,920 Tokens (过度搜索 2 步) | **严重失控！** 盲搜 8 步，耗尽 2,140 Tokens 产生幻觉 | 循环发散，近义词自旋 6 步 |
| **Strategy 2** | **静态硬限 (Static Hard Cap)** | 固定固定 `MaxSteps = 3`，超时即砍断 | 刚好在硬限前完成，但在 4 步链条中必然早夭 | 耗满 3 步配额，浪费 630 Tokens | 耗满 3 步配额，无法识别环路 |
| **Strategy 3** | **规则熔断 (Heuristic Breaker)** | 连续 2 次空召回熔断 + 环路探测 Jaccard $\ge 0.75$ | 召回率 100%，消耗 1,310 Tokens | **第 2 步光速熔断！** 消耗 430 Tokens 诚实拒答 | **第 4 步精准切断自旋！** 拦截率 100% |
| **Strategy 4** | **自适应调度 (Adaptive Controller)** | 边际增益 $\Delta I$ 监控 + 置信度饱和早停 + 多维硬墙 | **完美范式！** 3 步闭环，消耗 1,210 Tokens，召回率 100% | **2 步极速诚实拒答！** 消耗 430 Tokens，零幻觉 | **识别语义自旋并早停！** 零 Token 浪费 |

## 5. 实验实测与关键数据量化

以基准用例 `trap-01-fictitious`（虚构产品 Delta 与 Omega）为例：

```text
【自由放任策略】
  总步骤数: 8 步
  总 Token 开销: 2,140 Tokens
  无效 Token 浪费: 1,920 Tokens (浪费比例: 89.7%)
  时延: 2,180 ms
  最终结果: 强行拼凑无关片段产生虚假结论

【自适应预算控制策略】
  总步骤数: 2 步 (Step 1 搜 Delta 0 命中 ➔ Step 2 交叉求证 Omega 0 命中 ➔ 触发连续空命中安全熔断)
  总 Token 开销: 430 Tokens
  无效 Token 浪费: 0 Tokens
  时延: 490 ms (提速 4.4 倍！)
  最终结果: “知识库中未收录名为 Delta 或 Omega 的相关记录，已触发防过度检索安全熔断。”
```

**实验结论**：
- **Token 节省率高达 $79.9\%$**；
- **时延降低 $77.5\%$**；
- **幻觉率彻底归零**，完成了从盲目发散到受控严谨的工程蜕变！

## 6. 思考题与第 13 课预告

### 6.1 第一性原理思考题

1. **静态硬限的局限性**：为什么在生产级智能体系统中，简单设置 `maxSteps = 3` 是极其危险的？它与自适应预算控制器的本质区别在哪里？
2. **边际增益的冷启动**：如果一个复杂任务的前 2 步只是检索了背景目录（增益较低），直到第 3 步才定位到核心代码，简单的边际增益监控会不会误杀有效检索？底层应该如何设计窗口平滑（Window Smoothing）机制？
3. **拒答的艺术**：当触发连续空召回熔断时，为什么向用户输出“触发防过度检索熔断，未收录该实体”比直接返回 HTTP 500 或瞎猜更符合企业级交付标准？

---

### 6.2 已知未解与第 13 课预告：检索出的上下文怎么进入模型？

在第 12 课中，我们终于给脱缰的 Agent 戴上了缰绳，通过自适应预算控制器成功遏制了过度检索，将探索严格锁定在最高信噪比的 2~4 步之内。

但是，一个新的物理问题立即迎面而来：
即便只执行了 3 步检索，我们拿到了：
- **系统提示词 (System Instructions)**；
- **用户原始提问 (User Query)**；
- **工具调用的中间思考与历史 (Scratchpad / Tool History)**；
- **检索出来的 3~5 个文档父切片与结构标题 (Evidence Snippets)**；
- **企业通用规范与格式约束 (Negative Constraints)**。

这些总计 2,000~4,000 Tokens 的不同语义切片，**应该以什么样的拓扑结构装配进模型？**
- 证据应该放在 Prompt 前面还是后面？
- 会话历史很长时，如何压缩中间的工具输出只保留判决性事实？

👉 **第 13 课：检索出的上下文怎么进入模型？—— 上下文装配与布局几何学（Context Assembly & Layout Geometry）**
